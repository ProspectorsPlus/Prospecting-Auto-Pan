Verify a download

Every Prospector Lite 5.0.0 release file has a published SHA-256 checksum, and a matching checksum proves your download is byte for byte the file that was released. This page covers the whole subject: what the check proves, the exact commands on macOS and Windows, what every possible output means, and where the official values come from.

Why verify a download

Prospector Lite 5.0.0 ships unsigned on both platforms: no Apple notarization on macOS and no Authenticode signature on Windows yet. That means the operating system cannot vouch for the file on its own, so the release covers the gap with checksums. The build pipeline publishes a SHA-256 fingerprint for every release file, you recompute the fingerprint of your copy locally, and if the two values match, your file is identical to the one that was released.

The check is small. It uses a tool that already ships with your operating system, takes one command, and finishes in about a minute. It is worth running on every download, and essential for a copy that came from anywhere other than the GitHub release.

Verification never weakens anything. You never need to disable Gatekeeper, SmartScreen, or antivirus to verify a file, and no genuine instruction from this project will ever ask you to.

What SHA-256 is

SHA-256 is the recipe that computes the fingerprint. It reads every byte of a file, in order, and condenses them into a 64-character code of letters and digits. Two properties make that code useful here. First, it is extremely sensitive: changing a single byte anywhere in the file produces a completely different code, not a slightly different one, so there is no such thing as a near match. Second, it is one-way: the code can be computed from the file, but nobody can construct a different file that produces the same code. Put together, a matching code means an identical file.

Both platforms ship a tool that computes it: shasum on macOS and Get-FileHash in PowerShell on Windows. There is nothing to install.

What SHA256SUMS.txt contains

SHA256SUMS.txt is a plain text file, 771 bytes in total, attached to the release as its own asset (direct download). Its first three lines are the three builds:

SHA256SUMS.txt, first three lines
878cbff01e8bb2b597a2dfdb1c3a613406895cd59d933dc941a5ccf3fd5f6562  ProspectorLite-5.0.0-macos-arm64.dmg
242081f0dea0cd2aaf5b502ce425c6ea9b6cf883e5e1ac8add293c2364338102  ProspectorLite-5.0.0-Windows-x64-Setup.exe
b0c035b9cd3697e6e6758c8e4e24cd4a2dc3965b900d930cd7407198725921e9  ProspectorLite-5.0.0-Windows-x64-Portable.zip

Each line has two columns: the 64-character SHA-256 fingerprint, then two spaces, then the filename it belongs to. That two-column layout is the standard checksum-list format, which is why the macOS command below can read the file and do the comparison for you. The remaining lines cover the rest of the release the same way: the source archive, the two SBOM files, the release notes, and the release manifest, so every asset in the release can be verified the same way.

Verifying on macOS

You need two files sitting in the same folder: the DMG and SHA256SUMS.txt. Browsers save both to your Downloads folder by default, and the macOS download page links both if you still need them.

  1. Open Terminal: press Command + Space, type terminal, and press Return.
  2. Move Terminal into your Downloads folder:
    Terminal
    cd ~/Downloads
  3. Check your files against the published list:
    Terminal
    shasum -a 256 -c SHA256SUMS.txt --ignore-missing
  4. Read the result. You want exactly this line:
    Expected output
    ProspectorLite-5.0.0-macos-arm64.dmg: OK

What the pieces mean: -a 256 selects the SHA-256 algorithm, -c tells shasum to check files against a list instead of printing new fingerprints, and --ignore-missing keeps it quiet about the other release files named in the list that are not in your folder. If you also downloaded other release assets into the same folder, each one gets its own OK line.

Verifying on Windows

The same two-files rule applies: your download and SHA256SUMS.txt in one folder. Press the Windows key, type powershell, press Enter, then move PowerShell into your Downloads folder:

PowerShell
cd "$HOME\Downloads"

Windows has no direct equivalent of the macOS list-checking command, so there are two ways to compare. The first is to compute the fingerprint and compare it yourself:

PowerShell
Get-FileHash ".\ProspectorLite-5.0.0-Windows-x64-Setup.exe" -Algorithm SHA256

PowerShell prints the fingerprint in capital letters; letter case does not matter, but every character does. The published values to compare against:

Installer:
242081f0dea0cd2aaf5b502ce425c6ea9b6cf883e5e1ac8add293c2364338102

Portable ZIP:
b0c035b9cd3697e6e6758c8e4e24cd4a2dc3965b900d930cd7407198725921e9

The second way is to let PowerShell do the comparison. Paste this whole block and press Enter; it reads the published fingerprint out of SHA256SUMS.txt, computes the fingerprint of your download, and compares them for you:

PowerShell
$file = "ProspectorLite-5.0.0-Windows-x64-Setup.exe"
$expected = (Select-String -Path ".\SHA256SUMS.txt" -Pattern ([regex]::Escape($file))).Line.Split(" ")[0]
$actual = (Get-FileHash ".\$file" -Algorithm SHA256).Hash.ToLower()
if ($actual -eq $expected) { "OK: $file matches the published fingerprint" } else { "MISMATCH: do not run this file" }
Expected output
OK: ProspectorLite-5.0.0-Windows-x64-Setup.exe matches the published fingerprint

Downloaded the portable ZIP instead? Change the first line to $file = "ProspectorLite-5.0.0-Windows-x64-Portable.zip" and run the same block.

What OK means

OK makes three claims at once: the bytes on your disk are identical to the bytes of the released build, the download completed fully, and nothing altered the file in transit between the release and your computer. That is the whole claim, and it is exactly the claim you need before running an unsigned executable.

What it does not do is judge the software itself. A matching checksum proves you have the released build; whether that build deserves to run on your computer is a separate question, and it is answered by the public source code and the Trust and permissions page, which documents what the app can and cannot touch.

What a mismatch means

On macOS a bad file prints FAILED; the Windows comparison block prints MISMATCH: do not run this file. Both mean the same thing: the file on your disk is not the released build. On macOS the failure looks like this:

Output on a corrupted file
ProspectorLite-5.0.0-macos-arm64.dmg: FAILED
shasum: WARNING: 1 computed checksum did NOT match

The usual cause is mundane: an interrupted or incomplete download. The fix is three steps: delete the file, download it again from the release page, and run the check again. If the second copy also fails, stop and report it, including where the file came from. Never run, open, or install a file whose checksum does not match, whatever the explanation turns out to be.

Common errors

Three outputs come up regularly, and none of them is a verdict on the file; they mean the check could not run at all.

  • The checksum list is missing, or the terminal is in the wrong folder:
    Error output
    shasum: SHA256SUMS.txt: No such file or directory
    shasum could not find SHA256SUMS.txt in the current folder. Run cd ~/Downloads again, then ls to list what is there. If the list is not in the listing, it was saved somewhere else or under another name (see below).
  • The list is present, but none of the files it names are:
    Error output
    shasum: SHA256SUMS.txt: no file was verified
    shasum read the list, but not one of the files it names exists in this folder, so nothing was checked. Usually the build is still downloading, was saved to a different folder, or was renamed.
  • PowerShell reports a missing path. An error naming a file it cannot find (for example Cannot find path) means PowerShell is not in the folder that holds your downloads, or the file has a different name. Run cd "$HOME\Downloads" again, then dir Prospector*, SHA256* to see what is actually there.

Browser-renamed files

Downloading SHA256SUMS.txt a second time does not overwrite the first copy. On both platforms the browser saves the new one as SHA256SUMS (1).txt, and the check then fails to find the name it expects. Two fixes, both fine:

  • Rename it back. In Finder or File Explorer, delete the older copy and rename the new one to SHA256SUMS.txt. On Windows you can also do it in PowerShell:
    PowerShell
    Rename-Item ".\SHA256SUMS (1).txt" "SHA256SUMS.txt"
  • Or point the command at the renamed file, keeping the quotes. On macOS:
    Terminal
    shasum -a 256 -c "SHA256SUMS (1).txt" --ignore-missing

The quotes matter because the renamed filename contains a space and parentheses. Quoted, the shell treats SHA256SUMS (1).txt as one filename; unquoted, it reads three separate words and the command fails. The same rule applies in PowerShell, where unquoted parentheses have their own meaning.

Where the official checksums come from

The checksums are not written by hand. When the v5.0.0 tag was pushed, the tag-triggered GitHub Actions release pipeline built the release at the tagged commit, computed the SHA-256 value of every asset, and attached the result to the release as SHA256SUMS.txt. The pipeline definition is public, pinned to the same tag, so you can read exactly how the file was produced: .github/workflows/release.yml at v5.0.0.

A checksum is only as trustworthy as the place you got the expected value from, so take both sides of the comparison from the source. The three references:

  • The v5.0.0 GitHub release, where every asset lives.
  • The SHA256SUMS.txt asset on that release.
  • The release workflow at the tagged commit, which produced it.

The only official download locations are the GitHub release and this site's download pages, which link straight to it. If a build and its checksum file both came from a third-party site, a matching checksum only proves the two files agree with each other, not that either one matches the release.
