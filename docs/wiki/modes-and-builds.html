Modes, presets and builds

Prospector Lite runs a Standard loop by default, plus three farm modes (Treasure Chest, Shards, Geodes) that rewire the loop for one specific farm and a watch-only Tracker for benchmarking. Quick presets load a tuned starting point in one click, and the Builds tab saves your whole setup, relics included, under one name. This page covers how the modes interact, what each mode setting does, and how builds are saved, shared and imported as .ppbuild files.

How the modes fit together

Most builds run Standard, which is no mode toggled at all: the full dig, walk, shake, land loop. A mode rewires that loop for one specific farm. Each mode is a settings tab with a master switch at the top; turn the switch on and that tab's settings start to matter. The three farm modes live in the sidebar under the collapsible Modes group as the tabs "Treasure chest", "Shards" and "Geodes". The watch-only Tracker sits under the Tracking group next to Earnings.

What happens if more than one mode is on

The tabs do not lock each other out, so it is possible to leave two mode switches on at once. The app's own guidance is simple: run only one mode at a time, and each mode's help text tells you which switches to turn off (Treasure says to turn Shards and Geodes off; Geodes says to turn Shards and Treasure off). If several are left on anyway, the engine resolves the overlap by a fixed order: Tracker wins over an active Studio script, a script wins over Treasure, and Treasure wins over the normal cycle. Geode and Shards behavior lives inside the normal cycle's dig phase, so either of them yields to Tracker, a script, or Treasure. The run's History entry is labeled by the mode that actually ran.

While a Studio script is active, the Run tab says so in plain terms: the note under the picker reads that the script "runs instead of the built-in mode toggles." One exception hides behind the scenes: because Tracker outranks scripts inside the engine, the app parks your Tracker toggle while a Studio program is active and restores it when you switch back to Classic. You do not have to manage that yourself.

Which settings act in which mode

Mode settings are dormant outside their mode. That means you can keep a tuned Geodes tab and a tuned Shards tab side by side; only the one whose master switch is on has any effect. Everything not listed below is shared by all modes: calibration, the Standard cycle timings, recovery and safe-stop policy, relics, notifications, auto-stop and earnings tracking.

Treasure Chest mode

The app introduces it as "A no-shake mode for farming the two spots at Rubble Creek: stand on the deposit, it digs, strafes across to the sands, digs, then strafes back, over and over. Calibrate the Deposit pixel on the Collect prompt." Mechanically it is a separate, much simpler loop: dig briefly, then strafe sideways (right, then left, alternating) until the Collect Deposit cue shows again, then dig. There is no walk-back, no shake and no landing phase; the Cycle preview panel shows the chain as dig deposit, strafe to sands, dig, strafe back.

Use it when you are farming the two-spot Rubble Creek layout, where the normal shake loop has nothing to do. It navigates entirely by the Collect Deposit cue, so the Collect Deposit pixel must be calibrated on the Collect prompt first; see the calibration guide. To start: stand on the Rubble Creek deposit, calibrate the cue, turn the mode on and press Start.

The in-app help is explicit: "turn Shards and Geodes OFF when using this." Treasure outranks both in the engine, but leaving them on invites confusion when you later switch back.

Treasure chest settings

5 settings

Treasure Chest mode (no shake, strafe L/R)

toggledefault: off

The master switch. The in-app help calls it "The Rubble Creek two-step": no shaking, just dig, strafe across, dig, strafe back. All other settings on this tab are inert until this is on.

Turn it on when you are standing on the Rubble Creek deposit with the Collect Deposit pixel calibrated, and you want the two-spot farm instead of the shake loop.
Keep it off when you run any normal water farm; the Standard loop handles those.

Related: Delay between dig clicks, Max strafe before moving on. Watch for: the shake loop doing nothing useful on the two-spot farm; that is the symptom this mode exists for.

Digs per spot before strafing

numberdefault: 1

How many digs it performs at each spot before strafing to the other one. Usually 1: dig once and move on.

Raise it when a single dig does not finish before it starts moving.
Lower it when you raised it experimentally and the extra digs add nothing; 1 is the normal value.

Coach range: 1 to 10. Related: Quick dig click, Delay between dig clicks.

Quick dig click (ms)

numberdefault: 8 ms

The length of the dig click in this mode. Per the in-app help, 5 to 10 ms is the working zone: the click only needs to register, the dig animation does the rest.

Raise it when treasure digs are not registering at all.
Lower it when you have headroom and want the click as short as possible; below about 3 ms there is nothing to gain.

Coach range: 3 to 30 ms. Related: Delay between dig clicks.

Delay between dig clicks (ms)

numberdefault: 12000 ms

The wait between dig clicks while the slow chest-style animation plays out, so clicks do not stack. This is a hard wait per dig, so it directly sets the pace of the whole loop.

Raise it when digs overlap on slow gear; the in-app help suggests about 12000 ms as a good start.
Lower it when fast gear wastes time waiting between digs.

Coach range: 1000 to 30000 ms. Related: Digs per spot before strafing. Watch for: digs landing on top of each other; that means this value is too low for your gear.

Max strafe before moving on (ms)

numberdefault: 2500 ms

The strafe cap: stop strafing after this long even if the Collect cue never appears, so it cannot run sideways forever. The cap applies on each leg of the strafe, so a value that is too low stops the character short of the second spot.

Raise it when the two spots are far apart and it gives up before arriving.
Lower it when you want a missed cue to waste less walking.

Coach range: 800 to 6000 ms. Related: the Collect Deposit pixel on the Calibrate tab. Watch for: the character stopping between the spots and digging thin air.

Shards mode

Shards mode is exact-click digging for builds where a known number of clicks fills the pan; on a shards farm that number is usually one. The page hint reads: "Exact-click digging for shard farming: a known number of dig clicks (usually ONE), a registration check instead of probe re-digs, and optionally move on the moment the fill starts." There is no separate on/off toggle: setting "Exact dig clicks (0 = off)" above zero is what turns the mode on.

Mechanically, the mode replaces the dig phase only. It clicks the dig the set number of times per land visit, with no probe re-digs and no double clicks from bar-detection races: the first click must prove it landed (the capacity bar must leave empty within the confirm window), and only a provably dead click is retried. The rest of the cycle, walk back, shake and land, is the Standard loop. The tour sums up the point of it: this is the cure for fast builds double-digging.

Shards settings

5 settings

Exact dig clicks (0 = off)

numberdefault: 0 (off)

The mode's master switch. The in-app help: click the dig exactly this many times per land visit, no probe re-digs, no double clicks from bar-detection races. At 0 the mode is off and the normal dig logic runs.

Set it when a fixed number of clicks (often one) fills your pan and fast gear keeps digging 2 to 3 times before the bar moves.
Keep it at 0 when your fill count varies; the Standard dig logic reads the bar and adapts.

Coach range: 0 to 8. Related: Green dig-bar confirms the click, Assume full once the bar moves. Watch for: double-digging on very fast builds; that symptom is what this mode removes.

Bar must leave empty within (ms)

numberdefault: 100 ms

The proof window per click: the capacity bar must leave empty within this long, or the click is declared dead and retried. Only a provably dead click is retried, so a slow animation can never cause a double dig. The engine keeps a floor of 30 ms under whatever you enter.

Raise it when good clicks are being retried because your bar reacts slowly.
Lower it when you want dead clicks detected sooner on a build with a fast-reacting bar.

Coach range: 40 to 400 ms. Related: Max clicks if the bar never moves. Watch for: retries appearing in the log on clicks that clearly landed.

Max clicks if the bar never moves

numberdefault: 3

The dead-click budget: if the bar never moves, how many total clicks to try before deciding you are off land and nudging forward.

Raise it when good digs are abandoned too early.
Lower it when it wastes clicks on empty air.

Coach range: 1 to 6. Related: Bar must leave empty within.

Assume full once the bar moves

toggledefault: off

Skips the full read. The instant the bar starts filling, the pan is treated as full and the loop moves on; the walk to water happens during the fill animation, so the animation time is spent traveling instead of waiting. The shake clears the assumption automatically.

Turn it on when you run a one-click-fill build and want to remove the dead time waiting out the fill animation.
Keep it off when more than one click fills your pan; the assumption is only safe on one-click fills.

Related: Exact dig clicks. Watch for: arriving at the water with a pan that is not actually full.

Green dig-bar confirms the click

toggledefault: off

Green-bar proof: uses the dig skill-bar popping up as proof that the click registered, frames before the capacity bar moves, which per the in-app help can lag by 2 to 3 whole animations. Requires the Green dig pixel calibrated on the Calibrate page. Perfect mode itself can stay off. The check auto-disarms for the visit on green terrain, where the pixel test would be meaningless.

Turn it on when you run a very fast build where the capacity bar lags behind reality and good clicks keep getting retried.
Keep it off when the Green dig pixel is not calibrated, or the capacity-bar proof alone is already reliable on your build.

Related: the Green dig pixel step in the calibration guide; the geode counterpart is Green dig-bar confirms the dig. Watch for: retries on clicks that visibly landed; that lag is what this proof removes.

Geodes mode

Geode gear can slow the dig so much (10 percent dig-speed shovels and similar) that the capacity bar lags the dig by a long beat. The Standard probe would time out mid-animation and issue a false "dig failed" nudge while the fill is merely still catching up. Geode mode taps the dig, then waits out the animation between taps: each per-dig wait ends early the instant the bar moves, and it nudges only when the first dig of a land round shows no movement at all after the whole wait. It then hands back to the normal cycle: walk to water and the momentum shake, not Treasure's sideways strafe.

The page hint adds one strong recommendation: "Turn on the green dig-bar confirm so a tap that MISSED nudges straight away instead of costing that whole animation." While the mode waits out an animation, the Run tab and the HUD show a live countdown labeled "geode fill" with the remaining seconds.

You rarely need to tune this tab by hand. The Builds page ships Geode Farm and Geode Farm 1-Tap, and the v3 preset loads full geode timings. Start from those.

Geodes settings

9 settings

Geode mode (slow-animation dig, normal shake)

toggledefault: off

The master switch. Built for very slow fills: it taps the dig, waits out the animation, then runs the normal walk-back and momentum shake. The in-app help notes that the HUD shows the animation countdown while it waits.

Turn it on when you run 10 percent dig-speed geode shovels or similar and see false nudges mid-fill.
Keep it off when your fill animation is normal speed; the Standard probe handles that fine.

Related: Animation delay per dig, Digs to fill. Watch for: the in-app note "turn Shards and Treasure OFF."

Digs to fill (0 = auto until full)

numberdefault: 0 (auto)

How many taps fill the pan on this build, waiting out each slow animation. At 0 it keeps digging until the bar actually reads full, which the in-app help recommends.

Set a number when the bar reads unreliably on your build and you would rather trust a fixed count.
Keep it at 0 when the bar reads correctly; auto is the recommended setting.

Related: Animation delay per dig, Wait for the bar to read full first.

Quick dig hold (ms)

numberdefault: 5 ms

The quick tap length; 5 to 10 ms per the in-app help. It only needs to register, "Animation delay per dig" does the waiting. The shipped Geode Farm 1-Tap build raises this to 15 ms.

Raise it when geode digs are not registering at all.
Lower it when taps register reliably and you want them as short as possible.

Related: Animation delay per dig.

Animation delay per dig (ms)

numberdefault: 1500 ms

The in-app help calls this "The big one": how long to wait for the slow geode fill after each tap before deciding it failed. The wait ends early the moment the bar moves, so a generous value costs little on a healthy dig. This is the setting that stops the false nudges.

Raise it when you still see nudging mid-animation and ruined fills; set it as high as your slowest geode animation. The in-app help suggests 1500 to 3000 ms; the shipped geode builds and the v3 preset use 12000 ms for the very slowest gear.
Lower it when your animation is quicker and a failed tap should be detected sooner (green confirm is the better fix for that).

Related: Wait for the dig to start, Green dig-bar confirms the dig. Watch for: nudges landing while the bar is visibly still filling.

Wait for the dig to start (ms)

numberdefault: 800 ms

The dig-start proof window: after clicking, how long to wait for the dig to actually start (green bar or capacity movement) before re-clicking. The animation timer only begins once a dig is confirmed running.

Raise it when your game is laggy to start digs.
Lower it when digs start promptly and you want failed taps re-tried sooner.

Related: Animation delay per dig, Re-taps if a dig won't start.

Green dig-bar confirms the dig

toggledefault: off

Green-bar proof, the geode version. Normally a tap that missed still costs the whole animation delay before the macro can tell, so a dig off the edge of the land burns roughly 12 seconds doing nothing before it nudges. The green dig-bar shows within frames; with this on, a tap with no green is re-tapped immediately, and an exhausted tap budget nudges straight away instead of waiting the animation out. It will not count green that was already showing before the tap, and if a dig ever registers with no green it disarms itself for the run and asks you to re-calibrate.

Turn it on when you run slow geode gear where one tap fills the pan and a missed tap wastes a whole cycle; both shipped geode builds and the v3 preset turn it on.
Keep it off when the Green dig pixel is not calibrated yet.

Related: the Green dig pixel step in the calibration guide, Re-taps if a dig won't start. Watch for: a 12 second pause before it nudges, or the run getting stuck clicking off land; both are the symptoms this fixes.

Re-taps if a dig won't start

numberdefault: 3

The re-tap budget when the green confirm is on: how many taps to try before deciding the spot is not land and nudging forward. Each try costs one "Wait for the dig to start". The in-app note is important: this is ignored unless "Green dig-bar confirms the dig" is on, because without that proof a re-tap can double-dig.

Raise it when taps genuinely miss a lot on your build.
Lower it when you want it to give up and nudge faster.

Related: Green dig-bar confirms the dig, Wait for the dig to start.

Wait for the bar to read full first

toggledefault: off

Double-checks the fill: after the set number of digs, also wait for the bar to actually read full before walking back.

Turn it on when your bar reads reliably and an early shake costs more than a moment of waiting; the shipped geode builds turn it on.
Keep it off when the bar is very laggy and you would rather trust the dig count.

Related: Digs to fill.

Max shake time (ms)

numberdefault: 8000 ms

The geode shake cap. The shovel slows the shake too, so this is the maximum time to keep shaking; it still stops the instant the pan reads empty. In geode mode the usual bail-if-still-full check is off, so a slow shake is never abandoned mid-drain.

Raise it when shakes are cut short with capacity left on slow gear; the shipped geode builds use 10000 ms.
Lower it when your shake drains well inside the cap and you want a stuck shake abandoned sooner.

Related: the shake stage on the Cycle page; see the settings reference. Watch for: the pan still holding capacity when the walk to land begins.

Quick presets

The sidebar carries a Quick presets block with four chips: "v1 · fast 1-dig", "v2 · multi-dig", "v3 · geode" and "Reset defaults". A preset is a partial settings patch, not a profile: clicking a chip writes only the keys that preset carries into the matching settings fields and confirms with a splash (for example "v1 fast 1-dig loaded"). Everything the preset does not mention keeps its current value. The tour's advice: "Not sure? Try v1, or load a saved Build."

v1 and v2: two dig profiles

The first two chips are small and surgical. Each touches three keys on the Standard dig stage and nothing else:

Reset defaults

"Reset defaults" writes the schema default into each settings field, returning the form to the values documented as defaults throughout this wiki. Like the other chips it fills the form; review the result and save it if that is what you want. Settings edits, a preset included, can be stepped back with Ctrl+Z.

Presets and builds solve different problems. A preset is a tuned starting point that patches a few fields; a build is your own full profile stored on disk under a name. Start from a preset, tune, then save a build.

The Builds tab

The Builds page states its own contract at the top: "Every build is a FULL settings profile (all tabs + relics). Load applies everything; Overwrite captures your current settings into that build; click a description to edit it."

What a build stores

A saved build contains all of your settings values from the schema, plus the relic rows (name, minutes, slot, clicks) and the "Enable relic timer" master switch, plus metadata: the description, created and updated dates, a use counter and the last-used date, and optionally an attached document. Three things are deliberately not in a build: calibrated pixels, the webhook URL and secret, and window settings. Loading merges the build over your active configuration, so those keep their current values. Compatibility works the same way; the tour puts it as: "Loading a build made on an older version keeps your current values for any settings it does not know about. Nothing gets zeroed."

Saving and loading

  1. Quick save from anywhere: the topbar has a field with the placeholder "build name" next to the "Save build" button. Saving toasts: Build "name" saved (all settings).
  2. On the Builds page, the toolbar's "save current as…" field with the "Save current" button does the same; an empty name is refused with "Enter a build name".
  3. "Load" on a card applies the whole profile at once, settings and relics, and shows a splash with the build's name. Loading also bumps the build's use counter and last-used date.
  4. "Overwrite" re-captures your current settings and relics into that build; its tooltip reads "Overwrite this build with the CURRENT settings".
  5. A load is a normal settings edit, so Ctrl+Z steps it back if you loaded the wrong one.

Search and sort

The search field ("Search builds…") filters by name and description as you type. The sort menu offers "Newest" (the default), "Oldest", "Most used", "Recently used" and an alphabetical option; ties in the other sorts break alphabetically. The usage sorts are powered by the use counter and last-used date that Load maintains, so your daily driver floats to the top on its own. With no builds saved the grid says "No builds yet, save your current settings above."; a search with no hits says "No builds match that search."

The build cards

Each card shows the build's name, its description, a stats line (settings count, relic count, times used, created date, last used date), and the four buttons: "Load", "Overwrite", "Export" and "Attach doc". Click the description text (or the "Add a description…" placeholder) to edit it inline; descriptions are capped at 500 characters. Deleting is a two-step confirm: the delete button arms itself as "sure?" for 2.5 seconds, and only a second click deletes.

The shipped builds

Two ready-tuned geode builds ship with the app, so a fresh install has a working geode setup on the Builds page from the first launch:

Built-in cards behave slightly differently: they have no Delete button, and a user build with the same name overrides the bundled one. Loading a built-in build, or editing its description, seeds a personal copy into your builds file first, so your edits are always yours.

Where builds live on disk

Builds are one JSON file, prospecting_builds.json, in your data folder: ~/Library/Application Support/Prospector Lite on macOS, %APPDATA%\Prospector Lite on Windows (running from source keeps it next to the scripts). The Trust Center's local data listing labels it "Saved builds". Reinstalling or updating the app leaves the data folder in place, so builds survive updates; a one-time migration from an old "Prospectors Plus" install copies the file into the new location without touching the old folder.

Sharing builds as .ppbuild files

Since version 4.2.0 a build can travel as a single file. "Export" on a card writes that one build (settings, description and any attached document) to a .ppbuild file through the normal OS save dialog; the file is JSON with a format marker, and the dialog also offers a plain .json filter. Send the file to a friend however you like.

"Import build…" in the toolbar opens a native file picker (it accepts .ppbuild and .json). The import path is deliberately conservative:

  1. The payload is parsed as data and checked against the settings schema; each known key is coerced to its declared type. A build file is never executed. A file that does not parse is refused with "That isn't a valid build file."; a valid file with nothing usable inside is refused with "No build data in that file."
  2. A name clash gets a numeric suffix, so an import never overwrites one of your own builds.
  3. The imported build's usage metadata is reset, and it arrives as a regular user build: editable, deletable, yours.

Doc attachments

"Attach doc" attaches one document to a build: the picker accepts Word, PDF, text, Markdown and image files, plus Studio .ppscript files, up to 8 MB ("File too large (max 8 MB)." past that). The attachment is stored inside the build entry itself, so it travels inside the single .ppbuild file on export and import. A card with an attachment shows the filename with a "Download Roblox build" button that writes the document back out, and a remove button. The intended use, per the app's tour: attach an equipment doc so the person receiving your build knows what gear to make.

An exported build cannot leak your private setup: builds never contain calibrated pixels, your webhook URL or secret, or window settings, so none of those are in the file you share. The attachment you add is the only free-form content inside.

Common questions

Can a .ppbuild file run code on my machine?

No. A build file is parsed as data and strictly validated: known settings keys are coerced to their declared types and everything else is handled as inert content. Nothing in the file is executed as program code.

Will importing a friend's build overwrite mine?

No. If the incoming name matches one of yours, the import is renamed with a numeric suffix. Your builds are only ever changed by your own Load, Overwrite and Delete actions.

Does an exported build include my calibration or webhook?

No. Builds never carry calibrated pixels, the webhook URL or secret, or window settings, so an export cannot contain them. The receiver calibrates on their own screen, which is also why a shared build works across different machines.

I loaded a build made on an older version. Are my newer settings gone?

No. Loading merges the build over your current configuration, so any setting the old build does not know about keeps its current value. Nothing gets zeroed.

Classic, Studio Build and Studio Script

Everything above lives in the Classic world: the built-in cycle, its modes, and .ppbuild profiles. Prospector Studio programs are a separate system. The app's Settings page describes the ownership split on its "Settings ownership" card: Classic owns the built-in cycle tuning (modes, dig, shake and walk timing, recovery, relics); Studio owns which Studio entry is active; and Shared settings are used by both kinds of run (calibration, game window, notifications, auto-stop, earnings tracking, keybinds and appearance). Studio builds and scripts are stored in their own library file, prospecting_scripts.json, not in your builds file.

In standalone Prospector Lite you meet Studio programs through the Run tab's Mode picker: the first option is "Built-in modes", and your Studio entries follow as "Script: name". While one is active it runs instead of the built-in mode toggles, as described above.

The launch mode strip

When Prospector Studio launches the app, a three-tab strip labeled Macro mode appears in the topbar in place of the picker: "Classic" (the proven built-in cycle: modes, routes, relics, recovery), "Studio Build" (tooltip: "Run a prospecting build authored in Prospector Studio") and "Studio Script" (tooltip: "Run a general-automation Studio Script through the same engine"). The strip is hidden in standalone Lite.

The strip enforces a strict invariant rather than guessing: Classic means no Studio entry is active; Studio Build requires an active build-kind entry; Studio Script requires an active script-kind entry. Switching mid-run is refused ("Stop the run first, then switch."), and Start refuses on a mismatch, naming the problem ("no build selected", "A Studio entry is still active", or "The active entry does not match the selected mode") instead of silently running the wrong program. The quickest fix is usually the one the in-app FAQ suggests: run the entry from its own tab, which flips the mode for you.

For the full Studio surface (the block editor, script kinds and the recorder), see the Studio section of the interface reference.
